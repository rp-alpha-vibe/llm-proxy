# AI Agent Rules

Этот файл — основной операционный регламент для ИИ-агентов в репозитории `llm-proxy`.

Цель процесса: **максимальная скорость хакатонной разработки без потери управляемости и проверяемости**.
Процесс не должен превращаться в отдельный проект. Если правило не снижает реальный риск и не помогает доказать готовность результата, оно не нужно.

## 1. Источники истины

Системные инструкции и ограничения используемого инструмента обязательны. Внутри проекта при конфликте использовать следующий приоритет:

1. Актуальные явные решения владельца проекта.
2. `AGENTS.md` — правила работы агентов.
3. `docs/REQUIREMENTS.md` — требования хакатона и принятые критерии.
4. Принятые записи в `docs/DECISIONS.md`.
5. `docs/ARCHITECTURE.md` — принятая архитектура и границы компонентов.
6. Актуальный код/тесты в пределах принятых требований и архитектуры.

Регламент работы не отменяет обязательный контракт хакатона. Если решение владельца противоречит ТЗ, показать последствия для сдачи и зафиксировать согласованное отклонение; не объявлять его соответствием ТЗ.
Нельзя молча заменять требование тем, что уже реализовано в коде.

## 2. Обязательный старт

Перед нетривиальной задачей агент:

1. читает `AGENTS.md`;
2. читает только релевантные разделы `docs/REQUIREMENTS.md`;
3. читает релевантные записи `docs/DECISIONS.md`;
4. для инженерной задачи читает релевантные разделы `docs/ARCHITECTURE.md`;
5. для задачи реализации сверяется с соответствующим epic/task в `docs/IMPLEMENTATION_PLAN.md`;
6. подключает только те skills, которые реально нужны задаче.

Использовать уже прочитанный актуальный контекст; перечитывать при изменении источника или нехватке нужного раздела. Не читать механически весь репозиторий и все skills.
Канонический текст skill: `.agents/skills/<name>/SKILL.md`. Если инструмент не зарегистрировал skill автоматически, прочитать этот файл напрямую и применить инструкции.

## 3. Главные принципы

1. **Think before coding.** Сначала понять цель, ограничения и способ проверки.
2. **Simplicity first.** Выбирать самое простое полное решение. Не добавлять инфраструктуру, абстракции, зависимости и универсальность без текущей необходимости.
3. **Small scope.** Менять только то, что нужно задаче. Не делать попутный рефакторинг.
4. **Acceptance first.** До реализации должны быть понятны наблюдаемые критерии готовности.
5. **Fresh verification.** Нельзя объявлять задачу готовой по старым тестам или уверенности модели.
6. **AI code is untrusted.** Сгенерированный код считается недоверенным до проверки.
7. **Facts over confidence.** Зелёный тест доказывает только то, что он действительно проверяет.

## 4. Лёгкий workflow

Для каждой нетривиальной задачи достаточно пройти семь шагов:

1. **Goal** — что должно измениться.
2. **Plan** — 3–7 конкретных шагов.
3. **Acceptance** — как доказать готовность.
4. **Implement** — минимальный работающий вариант.
5. **Test** — свежие релевантные проверки.
6. **Review** — отдельный проход по diff/поведению.
7. **Accept** — сверка с acceptance criteria.

Обычная задача требует одного короткого task brief в issue, PR, рабочем плане или сообщении агента. Requirements и architecture — разделы того же brief, только если нужны; отдельные документы и повторные описания не требуются. Переход между skills не требует отдельного агента.

Рекомендуемый формат:

```md
Goal:
Scope:
Plan:
Acceptance:
Verification:
Risks:
```

Для очевидной локальной правки достаточно 1–3 предложений с целью, планом и проверкой.

## 4.1. Объём проверки

Выбрать объём по затронутому поведению и риску, а не по числу строк diff:

| Изменение | Проверки |
| --- | --- |
| Локальное исправление | Проверка дефекта/результата, релевантная регрессия, просмотр diff. Для текста — ссылки и согласованность; не создавать бессмысленные тесты. |
| Детектор или правило маскирования | Затронутые и пересекающиеся типы ПД, positive/negative cases, round-trip; для hot path — локальный benchmark. |
| Общий движок, state store, concurrency или runtime | Регрессия затронутых модулей, failure paths и нагрузка для изменённого механизма; общий PII-движок проверять на всех категориях. |
| Сдача проекта | Все обязательные категории, полный нагрузочный профиль, доступность endpoint и проверка ZIP. |

Быстрый общий suite запускать целиком, если он доступен. Полный ручной аудит и длительные нагрузочные прогоны повторять только при риске общей регрессии или перед сдачей.
Готовность отдельной задачи не означает готовность продукта: отсутствующие будущие функции учитывать отдельно, не скрывать и не выдавать за выполненные.

## 5. Когда нужен requirements-analysis

Использовать `requirements-analysis`, если задача:

- вводит или меняет поведение;
- меняет API/контракт;
- меняет state machine, retry/idempotency или recovery;
- меняет security/privacy semantics;
- меняет acceptance criteria;
- содержит неоднозначность ТЗ, влияющую на реализацию.

Для локальной правки, которая просто восстанавливает уже принятое поведение, отдельный requirements brief не нужен.

## 6. Когда нужен backend-architecture

Использовать `backend-architecture`, если реализация должна выбрать или изменить хотя бы одно из следующего:

- границы модулей/сервисов;
- публичный API;
- состояние и его хранение;
- concurrency/idempotency/retry;
- новую runtime-зависимость, влияющую на архитектуру или эксплуатацию;
- security boundary;
- deployment/runtime;
- модель выполнения или SLO; локальная оптимизация в существующих границах требует проверки производительности, но не нового architecture brief.

Архитектурный раздел общего brief должен быть коротким и прикладным. Не создавать отдельные ADR, схемы и review-артефакты без необходимости.

## 7. Review после реализации

Для нетривиального изменения обязателен отдельный review-проход через `code-change-review`.

Review должен проверить:

- соответствие требованиям;
- happy path и failure paths;
- идемпотентность/retry/concurrency;
- отсутствие утечек ПД и секретов;
- качество тестов;
- accidental complexity;
- производительность, если затронут hot path.

Обычные изменения допускают **separated self-review**: тот же агент может сделать review отдельным проходом после реализации. Доменные skills добавляют разделы в этот проход, а не новые отчёты и повторное чтение всего diff.
Независимый reviewer обязателен для изменения security model, семантики хранения чувствительных данных, необратимой архитектуры или опасного изменения действующего внешнего runtime. Использование уже принятой модели само по себе не требует нового независимого review.
Исправить findings после review; затем повторить затронутые проверки и просмотр исправлений. Не перезапускать весь цикл без нового риска. Не считать проверку до исправления доказательством исправленного поведения.

## 8. Доменные проверки хакатона

Если изменяется обнаружение, маскирование или демаскирование ПД, обязательно использовать `pii-quality-review`.

Если изменяется hot path, regex/scanner, state store, concurrency, HTTP runtime или deployment, обязательно использовать `performance-review`.

Пользовательский UI проверяется через `ux-ui-review` только если в задаче реально есть интерфейс.

## 9. Финальная приёмка

Перед завершением нетривиальной задачи использовать `release-verification` в режиме task; при подготовке к сдаче — в режиме submission. Это краткая сверка уже полученных актуальных доказательств, не повторный аудит.

Минимальная приёмка:

- acceptance criteria выполнены;
- применимые свежие проверки пройдены; для исполняемых команд прочитаны результаты и exit codes;
- нужные domain reviews пройдены;
- нет открытого P0/P1;
- нет секретов или реальных ПД в коде, fixtures, логах и документации;
- известные ограничения названы честно.

Не требуются отдельные evidence commits, manifest SHA, многоступенчатые approvals и другие церемонии, если они не закрывают конкретный риск.

## 10. Time-boxing

Процесс должен помогать писать код, а не мешать ему.

Ориентир на суммарный процесс обычной задачи (brief + review + приёмка): 10–15 минут, без реализации и исполнения проверок. Для очевидной локальной правки — несколько минут. Это ориентир, не основание пропускать обязательную проверку или ждать до истечения времени.
При превышении объяснить конкретный риск или неопределённость и продолжить нужную работу; отдельное согласование только из-за времени не требуется.
На первых 2–3 задачах кратко отметить фактические затраты процесса в итоговом сообщении, чтобы проверить эти ориентиры. Отдельный журнал не нужен.

## 11. Решения владельца

Агент не принимает самостоятельно решения, которые существенно меняют:

- scope продукта;
- формат обязательного внешнего контракта;
- security/privacy model;
- хранение чувствительных данных;
- труднообратимую зависимость или архитектуру;
- стратегию, влияющую на оценку хакатона.

Если есть несколько материально разных вариантов:

1. кратко описать последствия;
2. дать одну рекомендацию;
3. запросить решение владельца.

Локальные, обратимые технические решения внутри согласованного scope можно принимать самостоятельно.

## 12. Безопасность ПД

Исходные персональные данные запрещено помещать в:

- application logs;
- telemetry/metrics labels;
- traces;
- exception messages;
- committed fixtures;
- документацию;
- screenshots и demo artifacts.

Для тестов использовать только синтетические данные.

Если исходные данные необходимо временно хранить для демаскирования, хранение должно быть минимальным, ограниченным по времени и изолированным от логов/метрик.

## 13. Git и изменения

- Перед изменениями проверить текущую ветку и состояние дерева.
- Не перезаписывать неизвестные изменения.
- Для нетривиальной работы предпочтительна task-ветка.
- Маленькие локальные правки допустимы прямо в `main`, если рабочее дерево чистое и риск низкий.
- Не делать force-push и destructive Git operations без явного разрешения.
- Перед merge/commit проверить diff на секреты, реальные ПД, лишние файлы и случайный refactor.

## 14. Документация

Обновлять документацию только если изменилась правда о системе.

- `docs/REQUIREMENTS.md` — только при изменении/уточнении требований.
- `docs/DECISIONS.md` — только для важных принятых решений и причин.
- `docs/ARCHITECTURE.md` — обновлять только при принятом изменении архитектуры или когда реализация доказала несоответствие зафиксированной схеме требованиям/метрикам.
- `docs/IMPLEMENTATION_PLAN.md` — execution roadmap; обновлять статусы/порядок только по фактическому прогрессу и принятым изменениям requirements/architecture.

Репозиторий — постоянная память проекта, но память не должна превращаться в свалку протоколов.

## 15. Что считается Done

Задача завершена, когда:

1. достигнут наблюдаемый результат;
2. acceptance criteria проверены;
3. применимые проверки выполнены для текущего изменения;
4. релевантный review завершён;
5. блокирующие дефекты устранены; запись о блокере не заменяет исправление;
6. документация обновлена только там, где реально изменилась система.

Если обязательный критерий не выполнен/не проверен или есть открытый P0/P1, verdict — `block`, статус задачи — `blocked`, не Done.
`pass with follow-up` допустим только при выполненных обязательных критериях и неблокирующих замечаниях.
Известный P0/P1 вне scope тоже назвать блокером сдачи и не скрывать за готовностью локальной правки. Если что-то не проверено, назвать это прямо.

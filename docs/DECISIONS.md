# Decisions

Здесь фиксируются только решения, которые реально влияют на архитектуру, безопасность, acceptance или способ работы команды.
Локальные технические детали сюда не заносятся.

## D-001 — Lightweight AI development process

Status: accepted

Decision:

- использовать короткий цикл Goal -> Plan -> Acceptance -> Implement -> Test -> Review -> Accept;
- не переносить в проект многоступенчатые manifests, evidence-only commits, обязательные ADR и независимые review для стандартных задач;
- requirements/architecture документы создавать только когда они закрывают реальную неоднозначность или риск;
- separated self-review допустим для стандартных изменений;
- independent review нужен только для высокорисковых изменений.

Reason:

Хакатон ограничен по времени. Процесс должен предотвращать дорогие ошибки, но не становиться отдельной работой.

## D-002 — Repository as project memory

Status: accepted

Decision:

Ключевые требования и важные решения должны жить в репозитории, а не только в истории чатов.

Reason:

Разработка продолжается в разных сессиях; без общего источника истины быстро появляется drift.

## D-003 — Проверки по риску и единый результат задачи

Status: accepted

Decision:

- использовать один task brief, один отдельный review с нужными доменными разделами и короткую приёмку;
- разделять проверку отдельного изменения и готовность к сдаче; объём определять по затронутому поведению, полный быстрый regression suite сохранять;
- считать невыполненный обязательный критерий или P0/P1 блокером, даже если он записан в отчёт;
- хранить skills в `.agents/skills/` и при отсутствии автоматической загрузки читать нужные файлы напрямую;
- измерять локальное PII-качество воспроизводимо по §6.1 `docs/REQUIREMENTS.md`, не выдавая его за официальный scoring.

Reason:

Владелец одобрил правки по аудиту: сохранить проверки качества и убрать повторную подготовку документов и полную приёмку продукта на каждой локальной задаче.

Уточнение владельца: реализацию выполняет DeepSeek. Используется общий `AGENTS.md`; инструкции и подключения для прежнего инструмента удалены.

## D-004 — Проверяемое демаскирование и критерии нагрузки

Status: accepted

Decision:

- проверять exact round-trip контракта и демаскирование нового ответа LLM как отдельные сценарии (§5.1 requirements);
- до реализации доступа согласовать совместимый с официальным запросом способ допуска тестера, сохранив ограничения и изоляцию потребителей (§3.1);
- применять локальные численные пороги нагрузки и определения метрик из §7.1 requirements; не выдавать их за официальный scoring;
- считать устойчивый 429 на demask после исчерпания retry результатом неуспешной операции; одиночный 429 ещё допускает успешный повтор.

Reason:

Владелец одобрил уточнения по сверке с ТЗ. Приёмка должна обнаруживать возврат исходного prompt вместо ответа LLM, несовместимость доступа тестера и подмену успешного RPS поданной нагрузкой.

## D-005 — Минимальная архитектура llm-proxy

Status: accepted

Decision:

- runtime: Python 3.12 + FastAPI + несколько Uvicorn worker processes;
- shared correlation state: Redis, ephemeral, persistence off by default;
- sensitive session state хранить только в AES-GCM encrypted form с ограниченным TTL; ключ инжектируется через secret/environment;
- `ProcessService` владеет state machine mask/retry/exact-unmask/LLM-response-unmask;
- PII detection выполняется локально in-process; network LLM/NER calls в hot path не допускаются;
- detectors, contextual resolution, overlap resolution и mask strategy разделены;
- baseline имеет `CompetitionMaskStrategy` для официальной проверки и внутреннюю `PlaceholderMaskStrategy` для однозначного product LLM-response demask; placeholder strategy не заявляется бонусной tokenization/detokenization feature;
- unknown/ambiguous placeholders при product demask остаются в тексте без изменения; guessing и cross-session/cross-consumer lookup запрещены;
- final PII type должен однозначно соответствовать обязательной policy-visible категории, даже если общий parser переиспользуется несколькими detectors;
- per-system policies отделены от core flow через `ConsumerResolver`/`PolicyRegistry`;
- способ идентификации AlfaSonar остаётся адаптируемой границей до официального подтверждения и не меняет тело `/process`;
- overload ограничивается bounded concurrency с 429/Retry-After; Redis failure — fail closed;
- deployment baseline: один app service + Redis; остальные инфраструктурные компоненты не добавляются без evidence.

Canonical design: `docs/ARCHITECTURE.md`.

Reason:

Архитектура закрывает обязательный API, качество/расширяемость PII, exact и product demask, shared state для нескольких workers, безопасность и целевые метрики при минимальном количестве runtime-компонентов. Владелец проекта явно одобрил её как baseline.

## D-006 — Сдача 23 сентября: ранняя отправка и честный статус нагрузки

Status: accepted

Decision:

- до 23 сентября 2026 года, 23:59 МСК, вести E5–E16 параллельными потоками из `docs/IMPLEMENTATION_PLAN.md`; ранний deploy, ZIP, проверка архива и материалы финальной формы имеют приоритет и не ждут завершения всех детекторов;
- завершить E4 по его собственному acceptance: воспроизводимые async-тесты и один реальный HTTP → Redis smoke, затем короткий review и checkpoint; будущие PII и load-функции не включать в E4;
- сохранить обязательные категории ПД, quality, шифрование, изоляцию, per-system policy, метрики, large-payload и целевые показатели ТЗ; не заменять отсутствующее поведение успешным exact round-trip;
- сохранить локальные пороги и измерения §7.1 как инженерный gate, но не считать его провал автоматическим запретом на отправку до дедлайна; не пройденное требование фиксировать как `block` и не заявлять его выполненным;
- использовать отдельные действия сайта: предварительная проверка ZIP и окончательная форма с ZIP, презентацией, ссылками на VCS и работающий URL. Скринкаст не отмечен обязательным.

Reason:

Владелец одобрил сокращение критического пути после сверки исходного ТЗ и формы организаторов. Последовательная зависимость deployment/packaging от всех эпиков создавала риск не успеть к обязательным внешним проверкам. Официальный tester допускает 429, а нулевой бюджет ошибок и p95 как жёсткий gate — внутреннее усиление команды; фактические показатели остаются обязательной частью честного отчёта.

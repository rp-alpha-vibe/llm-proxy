# Hackathon Execution Requirements

Источник истины для обязательных требований: ТЗ трека «Модуль безопасности персональных данных».

Этот документ — не пересказ ТЗ, а исполнимая спецификация проекта: **что строим, зачем, что обязательно должно работать и что проверяем перед сдачей**.
Командные критерии помечены как локальные и не выдаются за официальный scoring Альфы.

## 1. Что мы строим

HTTP-сервис защиты персональных данных между системой-потребителем и LLM:

```text
consumer -> PII protection module -> LLM
consumer <- PII protection module <- LLM
```

Сервис должен:

1. находить персональные данные в тексте;
2. маскировать их до передачи в LLM;
3. демаскировать ответ;
4. сохранять полезный смысл остального текста;
5. поддерживать разные политики для разных систем;
6. безопасно работать под высокой нагрузкой;
7. позволять добавлять новые типы ПД и правила без переделки всего сервиса.

## 2. Что считается успешной сдачей

Проект нельзя считать готовым к сдаче, пока не выполнены все обязательные пункты:

- пройдена обязательная автоматическая проверка качества кода;
- подготовлен ZIP только с исходным кодом, без зависимостей, build/output, VCS, coverage, кэшей, дампов, датасетов, медиа и бинарников;
- сервис развёрнут и доступен по URL;
- строго реализован `POST /process`;
- покрыты все обязательные категории ПД;
- маскирование и демаскирование проходят локальный воспроизводимый quality suite; официальный порог ТЗ — 95%, но локальная метрика не выдаётся за официальный scoring;
- exact round-trip возвращает исходную строку с сохранением символов, пробелов, пунктуации и регистра;
- обработаны retry, concurrent duplicates, overload и 429;
- подтверждена работа на целевом профиле около 1000 RPS; целевой latency — не более 1 секунды;
- отдельно проверены крупные payload до 100 000 токенов;
- реализованы per-system access/policy настройки и инструкция по настройке не длиннее 5 предложений;
- есть требуемые логи и метрики без исходных значений ПД;
- подтверждены минимизация и применимое шифрование чувствительных данных;
- нет открытых P0/P1 и непроверенных обязательных критериев.

Финальная проверка этих пунктов выполняется `release-verification` в режиме `submission`.

## 3. Обязательный API-контракт

### Endpoint

```http
POST /process
Content-Type: application/json
```

Request:

```json
{
  "payload": "<string>",
  "payload_id": "<string>"
}
```

Response 200:

```json
{
  "result": "<string>"
}
```

Другой успешный формат ответа недопустим.

### Пара mask -> unmask

Для каждого элемента проверки используется один `payload_id`:

1. новый `payload_id` + исходный текст -> вернуть замаскированную строку и сохранить соответствие;
2. тот же `payload_id` + ранее возвращённая маска -> вернуть исходную строку.

`payload_id` уникален для элемента в рамках прогона. Элементы датасета могут переиспользоваться.

### Retry и идемпотентность

Тестер делает до 2 retry, то есть до 3 попыток одного запроса.

Из требования идемпотентности следует командный invariant:

- повтор исходного payload с тем же `payload_id` должен снова дать ту же маску;
- payload, равный сохранённой маске для этого `payload_id`, должен дать исходный текст;
- существование `payload_id` само по себе недостаточно, чтобы считать запрос demask.

Этот invariant — инженерное следствие сочетания pair-contract и обязательных retry, а не отдельная формулировка ТЗ.

### 429 и invalid requests

- `429 Too Many Requests` допустим под нагрузкой;
- при 429 tester учитывает `Retry-After` и повторяет запрос;
- 429 не считается invalid request и не сбрасывает счётчик consecutive invalid requests;
- успешный ответ сбрасывает этот счётчик;
- после 5 invalid requests подряд прогон останавливается;
- если 429 не проходит на mask, demask для этого элемента не запрашивается;
- если 429 возникает на demask, результат учитывается и прогон продолжается;
- timeout одного запроса — 10 секунд; ответ дольше считается неответом.

HTTP и HTTPS допустимы. Self-signed HTTPS допускается проверяющей системой.

## 4. Обязательные категории ПД

Нужно идентифицировать и защищать:

- ФИО;
- дату рождения;
- место рождения;
- серию и номер паспорта;
- гражданство;
- орган, выдавший паспорт;
- код подразделения;
- дату выдачи паспорта;
- серию и номер водительского удостоверения;
- адрес и его части, включая страну, индекс, город, улицу, дом, квартиру и аналогичные компоненты;
- email;
- номер телефона;
- ИНН;
- номер платёжной банковской карты;
- CVV;
- PIN;
- имя держателя карты.

### Контекст обязателен

Похожий на ПД фрагмент не всегда является персональными данными.

Обязательные negative scenarios:

- публичное упоминание человека, например Александра Пушкина;
- адрес организации/отделения Банка;
- обычная дата, не относящаяся к человеку;
- длинное число, не являющееся банковской картой;
- PIN/CVV без достаточного контекста, если правило требует контекстной уверенности.

False positives входят в качество решения.

## 5. Варианты записи и корректность текста

Обнаружение должно учитывать как минимум:

- регистр;
- разные порядки компонентов даты;
- текстовое написание даты;
- разные записи серии/номера;
- разделяющие слова вроде «серия ... номер ...».

Демаскирование должно возвращать исходный текст с сохранением положения знаков.

Командный acceptance для сохранения смысла запроса:

- текст вне обнаруженных PII spans не изменяется;
- замена не должна повреждать соседний текст, порядок сущностей и структуру предложения;
- выбранный формат маски не должен без необходимости уничтожать контекст, нужный LLM.

Последний пункт проверяется локально и не заменяет официальный scoring.

## 6. Качество

ТЗ требует высокое качество идентификации/маскирования/демаскирования — 95%.

Официальная прямая проверка сравнивает результат с эталонной маской метрикой «нормированное span-based расстояние Левенштейна [0..1]».
Обратная проверка сравнивает результат с исходной строкой.

ТЗ не раскрывает точную формулу scoring и канонические маски всех типов. Не выдумывать их.

### 6.1. Локальная проверка качества команды

Использовать воспроизводимый синтетический корпус с вручную заданными expected spans/types/results.

Измерять:

- precision / recall / F1 по категориям на точном совпадении type + span;
- false positives;
- exact round-trip rate;
- результаты по каждой категории отдельно;
- общий regression suite.

В корпусе обязательны:

- positive basic cases;
- formatting/case variants;
- contextual positives;
- contextual negatives;
- multiple PII в одном тексте;
- overlap/conflict cases;
- сложные предложения.

Expected данные нельзя вычислять тем же detector-ом, который проверяется.

Перед оценкой фиксировать команду запуска, размер корпуса, baseline и локальные пороги.
Локальные метрики не тождественны официальному scoring; нельзя автоматически трактовать локальные 95% как прохождение требования Альфы.

## 7. Производительность и устойчивость

Обязательные требования:

- target RPS: 1000;
- целевой latency: не более 1 секунды;
- нагрузочный прогон примерно 5 минут по всем категориям;
- обработка текста до 100 000 токенов;
- корректная деградация при ошибках/недоступности компонентов;
- безопасное поведение при concurrency и повторной доставке.

Распределение размеров payload в официальной нагрузке не раскрыто. Не предполагать, что 1000 RPS и 100 000 токенов обязательно относятся к одному и тому же workload.

Полный performance acceptance задаёт `performance-review`.

## 8. Настройки и расширяемость

Сервис обязан иметь ограниченный список систем-потребителей.

Для каждой системы должно настраиваться:

- enabled/disabled доступ к модулю;
- список типов ПД для идентификации/маскирования;
- разрешено ли демаскирование.

Должна быть краткая инструкция настройки не более 5 предложений.

Командный acceptance для «просто подключить нового потребителя»:

- новая система с существующими правилами добавляется конфигурацией без изменения core-кода;
- изменение policy одной системы не меняет поведение остальных систем.

Командный acceptance для расширяемости:

- новый detector/правило добавляется через предусмотренную точку расширения;
- добавление нового типа не требует переписывать routing, state machine и существующие detectors.

## 9. Логи, метрики и безопасность

### Логи

Требуется:

- логирование основных этапов обработки;
- логирование обнаруженных **типов** ПД по каждому запросу;
- отсутствие исходных значений ПД в application logs, traces и exception messages.

### Метрики

Требуются:

- Latency;
- RPS;
- TPS (tokens per second).

Исходные защищаемые данные нельзя помещать в metric labels или технические метрики.

### Хранение чувствительных данных

Требуется минимизация и шифрование.

Если оригинальный payload хранится для последующего demask:

- хранить только минимально необходимое;
- ограничить lifecycle/TTL там, где это применимо;
- не дублировать данные в логах/метриках/debug artifacts;
- для внешнего или персистентного storage должно быть доказуемое шифрование и безопасное управление ключами/секретами;
- секреты и ключи не коммитятся в репозиторий.

Конкретную модель хранения фиксировать в архитектурном brief до реализации.

### Compliance boundary

ТЗ требует обработку в защищённом контуре и соответствие применимому законодательству РФ, нормативной базе, требованиям ЦБ и внутренним стандартам ИБ Банка.

В предоставленном ТЗ нет критериев, позволяющих команде доказать полное нормативное или внутреннее банковское соответствие.
Поэтому:

- не заявлять такое соответствие без предоставленных критериев и фактического evidence;
- реализовать проверяемые технические требования ТЗ: отсутствие утечек, минимизацию, шифрование, ограничение доступа, безопасные логи и устойчивость;
- внешний инфраструктурный/compliance gate отмечать отдельно, если организаторы предоставят дополнительные требования.

## 10. Обязательная упаковка и deployment

Для автоматической code-quality проверки:

- только один ZIP;
- только исходный код решения;
- не включать `node_modules`, `.venv`, `venv`, `env`;
- не включать `target`, `build`, `dist`, `out`, `bin`, `obj`;
- не включать `.git`, `.idea`, `__pycache__`, `coverage`;
- не включать объёмные datasets, dumps, archives, media и compiled binaries.

Для нагрузочного теста:

- сервис должен быть доступен по переданному URL на момент прогона;
- должен отвечать строго по контракту `POST /process`;
- deployment может использовать HTTP или HTTPS.

## 11. Бонусы, не блокирующие обязательную сдачу

После обязательного baseline можно добавлять:

- токенизацию/детокенизацию;
- замену синтетическими данными;
- гибкую настройку вида маскирования/токенизации по системе;
- 2000 RPS при latency <= 1 секунды;
- дополнительные документы, удостоверяющие личность;
- configurable masking только при наличии нескольких однозначно идентифицированных типов ПД.

Бонусная функция не должна ухудшать обязательные quality/performance/security criteria.

## 12. Открытые вопросы ТЗ

Официально не определены:

1. канонический формат маски для каждого типа ПД;
2. точная формула span-based scoring;
3. распределение и сложность эталонного датасета;
4. сочетание размеров payload с целевыми 1000 RPS;
5. детальные критерии внутреннего ИБ/compliance Банка.

Если решение зависит от неизвестного:

1. сначала искать официальный ответ/пример;
2. не подменять пробел догадкой;
3. выбрать минимально рискованное обратимое предположение;
4. явно записать assumption или запросить решение владельца, если оно влияет на сдачу.

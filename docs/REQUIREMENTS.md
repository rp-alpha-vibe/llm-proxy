# Hackathon Requirements

Источник: техническое задание трека «Модуль безопасности персональных данных», предоставленное владельцем проекта.

Этот документ фиксирует требования ТЗ, явно отмеченные инженерные решения по локальной проверке и открытые вопросы. Инженерные решения не являются официальным scoring хакатона.

## 1. Цель

Разработать сервис, который может работать как proxy/Core-компонент между системой-потребителем и LLM:

```text
consumer -> PII protection module -> LLM
consumer <- PII protection module <- LLM
```

Сервис должен:

- идентифицировать типы персональных данных;
- маскировать ПД до отправки в LLM;
- демаскировать ответ;
- работать быстро и стабильно под высокой нагрузкой;
- позволять расширять правила без переделки всей системы.

## 2. Обязательные типы ПД

Нужно покрыть:

- ФИО;
- дату рождения;
- место рождения;
- серию и номер паспорта;
- гражданство;
- орган, выдавший паспорт;
- код подразделения;
- дату выдачи паспорта;
- серию и номер водительского удостоверения;
- адрес и его части;
- email;
- номер телефона;
- ИНН;
- номер платёжной карты;
- CVV;
- PIN;
- имя держателя карты.

Нужно учитывать принадлежность данных именно к персональным: например, упоминание Александра Пушкина или адрес отделения банка не должны автоматически считаться ПД.

## 3. Варианты записи

Обнаружение должно учитывать как минимум:

- регистр;
- разные форматы дат;
- текстовое написание дат;
- варианты записи серии/номера;
- разделяющие слова вроде «серия … номер …».

## 4. Контракт автоматической проверки

Обязательный endpoint:

```http
POST /process
Content-Type: application/json
```

Request:

```json
{
  "payload": "<string>",
  "payload_id": "<string>"
}
```

Response 200:

```json
{
  "result": "<string>"
}
```

Логика пары запросов:

1. Первый запрос с новым `payload_id`: `payload` содержит исходный текст. Сервис возвращает маску и запоминает соответствие.
2. Второй запрос с тем же `payload_id`: `payload` содержит ранее возвращённую маску. Сервис возвращает исходную строку.

`payload_id` является ключом корреляции mask -> unmask.

## 5. Надёжность автоматической проверки

- timeout одного запроса: 10 секунд;
- до 2 retry, то есть до 3 попыток;
- endpoint должен быть идемпотентным по `payload_id`;
- `429 Too Many Requests` допустим под нагрузкой, tester учитывает `Retry-After`;
- после 5 невалидных запросов подряд прогон останавливается;
- элементы датасета могут переиспользоваться.

Следствие для реализации: retry первого шага и второй шаг пары нельзя различать только по факту существования `payload_id`.

## 6. Качество

ТЗ требует высокое качество идентификации/маскирования/демаскирования — 95%.

При прямой проверке результат сравнивается с эталонной маской метрикой «нормированное span-based расстояние Левенштейна [0..1]».

При обратной проверке результат сравнивается с исходной строкой.

### 6.1. Локальная проверка качества (решение команды)

- Использовать воспроизводимый синтетический корпус с явно заданными типами, границами ПД и ожидаемыми результатами; включать неперсональные примеры и пересечения.
- Измерять precision/recall/F1 по типам на точном совпадении типа и span, отдельно считать false positives и долю точных round-trip. Указывать размер корпуса и число примеров по категориям.
- Локальной задаче задавать критерии для затронутого поведения; при общей приёмке показывать все обязательные типы и непокрытые категории. Не скрывать слабую категорию общим средним.
- Зафиксировать команду, baseline и принимаемые пороги до оценки реализации. Локальные метрики не тождественны официальному span-based scoring; 95% из ТЗ нельзя автоматически приписывать любой выбранной метрике.

## 7. Производительность

Требования:

- target RPS: 1000;
- ориентир latency: не более 1 секунды;
- крупные тексты: до 100 000 токенов;
- дополнительный плюс: 2000 RPS при latency <= 1 секунды;
- нагрузочный прогон примерно 5 минут.

## 8. Настройки и безопасность

ТЗ требует:

- ограниченный список систем, имеющих доступ к сервису;
- включение и отключение доступа каждой системы;
- настройку типов ПД по системе;
- настройку возможности демаскирования по системе;
- гибкий вид маскирования/токенизации как дополнительный плюс;
- подробное логирование этапов;
- логирование обнаруженных типов ПД для каждого запроса без исходных значений;
- метрики latency, RPS, TPS;
- отсутствие исходных защищаемых данных в логах и технических метриках;
- шифрование и минимизацию данных;
- корректную деградацию при ошибках/недоступности компонентов;
- краткую инструкцию настройки длиной не более 5 предложений.

## 9. Дополнительные плюсы

- токенизация/детокенизация;
- синтетическая замена;
- 2000 RPS;
- дополнительные документы, удостоверяющие личность;
- контекстное маскирование только при наличии набора однозначно идентифицированных ПД.

## 10. Обязательные проверки сдачи

Решение должно:

- пройти автоматическую проверку качества кода;
- быть упаковано только исходным кодом в ZIP без build/dependency/runtime-мусора;
- быть развёрнуто и доступно по URL для нагрузочного теста;
- строго реализовывать контракт `POST /process`.

## 11. Открытые вопросы ТЗ

ТЗ не фиксирует однозначно:

1. канонический формат маски для каждого типа ПД;
2. точную формулу span-based scoring;
3. распределение и сложность эталонного датасета;
4. реальные границы сочетания «1000 RPS» и «до 100 000 токенов» в одном профиле нагрузки.

Агенты не должны выдумывать ответы на эти вопросы.
Если решение зависит от них, нужно:
- сначала искать официальный ответ/пример;
- затем выбрать минимально рискованное предположение;
- явно записать его как assumption или решение владельца.

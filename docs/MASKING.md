# Как работает маскирование и восстановление персональных данных

Этот документ подробно объясняет реализованный в **llm-proxy** алгоритм: как сервис находит персональные данные, заменяет их обозначениями, запоминает соответствия и восстанавливает сведения в ответе языковой модели. Сначала описан принцип работы на примере, затем приведены технические детали и ограничения.

**Границы системы:** llm-proxy не отправляет запросы языковой модели и не получает её ответы самостоятельно. Это делает приложение, которое вызывает наш сервис. Оба действия — маскирование и восстановление — выполняются через один адрес `POST /process`.

## 1. Весь процесс на одной схеме

```text
ПРИЛОЖЕНИЕ                            НАШ СЕРВИС
    │                                      │
    ├── исходный текст и payload_id ──────►│
    │                                      ├─ проверить правила приложения
    │                                      ├─ найти персональные данные
    │                                      ├─ заменить их обозначениями
    │                                      └─ сохранить зашифрованные соответствия
    │◄──────────── очищенный текст ────────┤
    │
    ├── очищенный текст ───────────────► ЯЗЫКОВАЯ МОДЕЛЬ
    │◄──────── ответ модели ────────────────┘
    │
    ├── ответ модели и тот же payload_id ─►│
    │                                      ├─ найти прежние соответствия
    │                                      ├─ восстановить известные обозначения
    │                                      └─ сократить срок хранения записи
    │◄───── ответ с восстановленными ──────┤
    │                 данными
    ▼
ПРИЛОЖЕНИЕ
```

`payload_id` — идентификатор одной последовательности обработки. По нему сервис понимает, какие данные можно восстанавливать. Его нужно повторно использовать **для ответа на тот же запрос**, но менять для новой независимой обработки.

## 2. Понятный пример

Используем только вымышленные адреса электронной почты.

**Первый запрос приложения:**

```json
{
  "payload": "Основной адрес: ivan@example.com. Запасной: anna@example.com.",
  "payload_id": "example-001"
}
```

Сервис обнаруживает два адреса и возвращает:

```json
{
  "result": "Основной адрес: <EMAIL_1>. Запасной: <EMAIL_2>."
}
```

Внутри одной временной записи он сохраняет соответствия:

| Обозначение | Исходное значение |
| --- | --- |
| `<EMAIL_1>` | `ivan@example.com` |
| `<EMAIL_2>` | `anna@example.com` |

Эта таблица приведена **только для объяснения**: сервис не публикует её через программный интерфейс и не хранит в Redis открытым текстом.

Приложение самостоятельно передаёт очищенный текст языковой модели. Предположим, модель ответила:

```text
Сначала напишите на <EMAIL_2>, затем на <EMAIL_1>.
В копию добавьте <EMAIL_2>.
```

Приложение отправляет **этот новый текст** нашему сервису, сохранив `payload_id: "example-001"`. Результат:

```text
Сначала напишите на anna@example.com, затем на ivan@example.com.
В копию добавьте anna@example.com.
```

Сервис восстанавливает известные обозначения независимо от их порядка и числа повторений. Он не подменяет ответ модели первоначальным запросом: все новые слова, пробелы и знаки препинания остаются на своих местах.

## 3. Как сервис решает, что делать с запросом

Оба действия выполняет `POST /process`. Формат запроса всегда одинаков: `payload` (текст) и `payload_id` (идентификатор последовательности). Успешный ответ содержит только `result` (обработанный текст).

После проверки формата запроса сервис выбирает заранее настроенные правила приложения и обращается к временному хранилищу.

| Что нашёл сервис | Что делает |
| --- | --- |
| Записи с этим идентификатором нет | Ищет персональные данные, маскирует их и создаёт временную запись |
| Запись есть, передан **точно исходный текст** | Повторно возвращает прежний замаскированный текст, ничего не ищет заново |
| Запись есть, передан **точно ранее возвращённый замаскированный текст** | Возвращает первоначальный текст целиком, посимвольно |
| Запись есть, передан **другой текст** | Пытается восстановить только известные однозначные обозначения внутри переданного текста |

Сравнение выполняется именно в этом порядке. Поэтому **наличие старого `payload_id` ещё не означает команду на восстановление**: запрос мог просто повториться из-за сетевого сбоя.

**Особый случай:** если персональные данные не найдены, исходный и замаскированный тексты совпадают. Тогда повтор такого текста обрабатывается как повтор исходного запроса; содержимое ответа всё равно не меняется.

Для нового независимого текста нельзя переиспользовать старый `payload_id`. Иначе сервис будет рассматривать новый текст как возможный ответ на предыдущую операцию.

## 4. Как обнаруживаются персональные данные

### 4.1. Учитываются настройки приложения

Сначала сервис получает правила для приложения, подключённого к данному развёртыванию. В правилах указано, какие категории искать, разрешено ли восстановление и какой формат обозначений использовать.

В реализованном публичном интерфейсе приложение **не выбирается полем или заголовком каждого запроса**: оно задаётся настройкой `LLM_PROXY_DEFAULT_CONSUMER_ID` при развёртывании. Набор доступных приложений определён в `config/systems.example.yaml`.

### 4.2. Текст подготавливается для поиска

Сервис создаёт рабочее представление текста. Из него удаляются несколько невидимых символов, мешающих обнаружению. При этом сохраняется соответствие позиций между рабочим представлением и **исходной** строкой. Регистр букв, кириллица и обычная пунктуация не изменяются.

Это нужно для того, чтобы заменить именно найденные части первоначального текста, не переписывая остальные символы.

### 4.3. Поиск выполняется двумя группами правил

**Проверка по форме записи:** электронная почта, телефон, ИНН, номер банковской карты, паспорт, код подразделения и водительское удостоверение. В необходимых случаях дополнительно проверяется структура номера: например, контрольные цифры ИНН и банковской карты.

**Проверка с учётом окружения:** ФИО, даты и места рождения, дата и орган выдачи паспорта, гражданство, адрес и его части, защитный код карты (CVV), ПИН-код и имя держателя карты. Таким фрагментам обычно требуются признаки, указывающие, что текст относится к конкретному человеку или документу.

Например, дата сама по себе ещё не обязательно является датой рождения, а адрес организации — личным адресом. Контекстные правила уменьшают число лишних замен, но не гарантируют безошибочное распознавание любой произвольной фразы.

Все проверки происходят **внутри приложения**: для распознавания не вызываются внешняя языковая модель или сторонний сетевой сервис.

### 4.4. Отбираются непересекающиеся фрагменты

Несколько правил могут претендовать на одни и те же символы. Сервис выбирает фрагменты по приоритету: сначала структурные проверки, затем подтверждённые контекстом, затем более общие. Внутри одного приоритета учитываются степень уверенности, длина совпадения и стабильные правила разрешения равенства.

Пересекающиеся кандидаты одновременно не заменяются. Итоговые позиции всегда относятся к первоначальному тексту. Замены применяются **справа налево**, чтобы вставка обозначения не сдвинула координаты ещё не обработанных фрагментов.

## 5. Как создаются обозначения

Каждому новому сочетанию **категории и точного исходного значения** присваивается обозначение. Одинаковое значение той же категории в пределах одной записи получает то же обозначение; различные значения — разные обозначения. Нумерация общая для всех категорий внутри записи и идёт по порядку обнаруженных фрагментов, а не отдельно для каждого типа.

Например, если первым обнаружена электронная почта, а вторым — телефон, номера могут выглядеть как `<EMAIL_1>` и `<PHONE_2>`.

Реализованы два формата, выбираемые настройкой приложения:

| Режим настройки | Вид обозначения | Для чего используется |
| --- | --- | --- |
| `competition` | `<EMAIL_1>` | Формат, выбранный командой для проверки хакатона |
| `placeholder` | `[[PII:EMAIL:1]]` | Другой формат, удобный для восстановления в ответах моделей |

**Важно:** формат `<EMAIL_1>` — собственное обратимое решение команды; он не заявляется подтверждённым эталоном организаторов.

Перед присвоением обозначения сервис проверяет, что оно не совпадает с уже использованными обозначениями, не является их частью (и наоборот) и не встречается в участках исходного текста, которые не подлежат замене. Если возникает конфликт, выбирается следующий номер. Это снижает риск ошибочного восстановления.

## 6. Что запоминается и как защищается

Для каждой последовательности обработки формируется временная запись. Она содержит исходный текст, замаскированный текст, найденные фрагменты с их исходными позициями и обозначениями, параметры выбранных правил и время создания.

Запись сохраняется в **Redis** — быстром временном хранилище, используемом совместно всеми рабочими процессами приложения. Ключ записи включает идентификатор приложения и результат криптографического хеширования `payload_id` алгоритмом SHA-256; сам исходный `payload_id` в ключ не записывается.

До записи в Redis содержимое целиком шифруется алгоритмом **AES-GCM**. Ключ шифрования передаётся приложению через настройки окружения и не должен попадать в репозиторий. Redis не открывается в интернет напрямую; в принятой конфигурации постоянное сохранение его содержимого на диск отключено.

**Срок хранения по умолчанию:** 15 минут с момента создания записи. После успешного восстановления срок сокращается до 2 минут, чтобы оставить небольшое время на повторные запросы. Эти значения можно изменить настройками. После истечения срока восстановить прежнее соответствие уже нельзя; при последующем запросе с таким же идентификатором и отсутствии записи сервис рассматривает его как новый запрос на маскирование.

Если Redis недоступен или сохранённую запись невозможно корректно прочитать, сервис возвращает ошибку и **не пытается восстанавливать данные по догадке**. Если повторный запрос приходит одновременно с первым, временная запись создаётся только один раз; проигравший одновременную запись запрос использует уже сохранённый результат.

## 7. Два способа восстановления

### 7.1. Точное восстановление

Если `payload` **посимвольно совпадает** с ранее выданным замаскированным текстом, сервис возвращает сохранённый исходный текст целиком.

Таким способом полностью восстанавливаются регистр, пробелы, невидимые символы и пунктуация оригинала. Новый поиск персональных данных при этом не запускается.

### 7.2. Восстановление внутри ответа языковой модели

Если текст отличается от исходного и полного замаскированного варианта, сервис ищет известные обозначения **только в соответствующей временной записи**. Он заменяет каждое обозначение исходным значением лишь тогда, когда соответствие однозначно.

При этом сервис:

- восстанавливает известные обозначения в любом порядке и при повторении;
- не добавляет отсутствующие в ответе данные;
- сохраняет все остальные части текста, сформированного моделью;
- оставляет неизвестные или неоднозначные обозначения без изменения;
- не обращается за соответствиями к другим записям или приложениям.

Для формата `[[PII:EMAIL:1]]` сервис также распознаёт незнакомые фрагменты аналогичного вида и оставляет их нетронутыми. Для другого формата восстанавливаются только обозначения, которые действительно известны из текущей записи.

**Ограничение:** восстановление опирается на точное присутствие обозначения в тексте. Если языковая модель произвольно изменила его написание, восстановление такого фрагмента не гарантируется.

### 7.3. Когда восстановление запрещено

Если правила подключённого приложения запрещают восстановление, запрос на него отклоняется. Запись одного приложения нельзя использовать для восстановления сведений из записи другого: ключи и правила обработки разделены.

## 8. Ошибки и границы алгоритма

- Неверный формат запроса отклоняется с кодом **422**; неизвестное или отключённое приложение — с кодом **403**.
- При превышении допустимого числа одновременно обрабатываемых запросов сервис может вернуть **429** и указать в заголовке `Retry-After`, через сколько секунд следует повторить попытку.
- При недоступности или повреждении временного состояния возвращается контролируемая ошибка **503**. Сервис не отдаёт исходные персональные данные как запасной способ обработки.
- В публичной текущей конфигурации отдельная авторизация `POST /process` не реализована. Её совместимость с официальной проверяющей системой организаторов проверяется отдельно; для публичной демонстрации используйте только вымышленные данные.
- Поиск основан на реализованных правилах и контекстных признаках. Локальные показатели качества на синтетических примерах не гарантируют такого же результата на любом реальном тексте.

## 9. Где находятся части реализации

Этот документ — единое объяснение алгоритма. Точная конфигурация и внутренние интерфейсы остаются в [архитектуре](ARCHITECTURE.md), а обязательные условия проверки — в [требованиях](REQUIREMENTS.md).

| Часть алгоритма | Реализация |
| --- | --- |
| Выбор действия по запросу, повтор и восстановление | `src/llm_proxy/application/process_service.py` |
| Обнаружение, учёт контекста и разрешение пересечений | `src/llm_proxy/detection/` |
| Присвоение обозначений и два формата масок | `src/llm_proxy/masking/` |
| Формирование записи, шифрование и Redis | `src/llm_proxy/state/` |
| Правила для приложений | `src/llm_proxy/policies/`, `config/systems.example.yaml` |
| Проверка и ответы `POST /process` | `src/llm_proxy/api/process.py` |

**Короткий словарь:** персональные данные (PII) — сведения о конкретном человеке; языковая модель (LLM) — система искусственного интеллекта для обработки текста; маскирование — замена данных обозначениями; демаскирование — обратное восстановление; Redis — временное хранилище; `payload_id` — идентификатор одной последовательности обработки; AES-GCM — алгоритм шифрования, одновременно позволяющий обнаружить изменение зашифрованной записи.

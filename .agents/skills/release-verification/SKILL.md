# Release Verification

Выбери режим: `task` для отдельной задачи или `submission` для готовности к сдаче.
Это сверка уже полученных доказательств, а не новый аудит. Не повторяй актуальные проверки без причины.

## Общие условия

1. Goal и обязательные acceptance criteria выполнены и имеют наблюдаемое доказательство.
2. Применимые проверки соответствуют текущему изменению; результаты и exit codes команд прочитаны.
3. Для нетривиального изменения выполнен отдельный `code-change-review`, включая применимые domain sections.
4. Нет открытых P0/P1.
5. В diff/artifacts нет секретов, реальных ПД и небезопасных runtime payloads.
6. Ограничения и непроверенные вещи названы честно.

Проверки до исправления findings не доказывают исправленное поведение: повтори затронутые проверки и просмотр diff.
Для документации проверяй согласованность и ссылки; не требуй runtime-тестов, если исполняемое поведение не менялось.

## Режим task

- Используй объём из `AGENTS.md`, §4.1.
- PII/performance/UI/security/observability — только применимые части общего review.
- Будущие функции вне принятого scope перечисли как product limitations; они не означают автоматический провал локальной задачи.
- Регрессии, обязательные критерии текущей задачи и P0/P1 нельзя переносить в follow-up ради статуса Done.

## Режим submission

Проверяй по `docs/REQUIREMENTS.md`, §2. Для удобства обязательный gate ниже.

### A. Packaging и external code check

- ZIP один, разумного размера, собран по allowlist и содержит только исходники решения и минимальные файлы сборки/запуска/конфигурации; внутренние project docs и agent instructions не включены без явного требования организаторов;
- отсутствуют dependencies, build/output, VCS, coverage, caches, dumps, datasets, media, binaries;
- обязательная автоматическая проверка качества кода фактически пройдена; если внешнего результата ещё нет, готовность к сдаче не подтверждена.
- для финальной формы отдельно подготовлены презентация, ссылка на VCS и URL работающего сервиса; проверка ZIP не заменяет окончательную отправку.

### B. Deployed API

- сервис доступен по заявленному URL;
- `POST /process` строго принимает `{payload, payload_id}` и возвращает `{result}`;
- доступ тестера подтверждён по §3.1: официальный запрос работает при согласованном допуске, несогласованных обязательных полей/заголовков нет, ограничения других потребителей сохранены;
- mask -> unmask пара работает;
- retry исходного payload с тем же id идемпотентен и не превращается в demask;
- concurrent duplicates не повреждают state;
- 429 использует корректный `Retry-After`; различены успешный retry после одиночного 429 и неуспех после исчерпания попыток (§3 requirements);
- timeout/failure paths не приводят к серии необработанных invalid responses.

### C. PII quality

- покрыты все обязательные категории из §4;
- есть positive/format/context/negative/overlap/multiple-PII cases;
- false positives проверены;
- exact round-trip восстанавливает исходную строку, включая знаки, пробелы и регистр;
- отдельные fixtures §5.1 подтверждают демаскирование нового ответа LLM с перестановкой/повторением масок и сохранением текста ответа; неизвестные/неоднозначные placeholders остаются без изменения; один round-trip не доказывает этот сценарий;
- non-PII части текста не повреждаются;
- качество измерено воспроизводимым локальным corpus по §6.1;
- локальная метрика не выдаётся за официальный scoring и официальный порог 95% не объявляется пройденным без внешнего evidence.

### D. Performance и reliability

- выполнен полный baseline с профилем, определениями метрик и всеми локальными порогами §7.1 requirements;
- зафиксированы offered и успешный RPS, p50/p95/p99/max latency, попытки, errors, 429, CPU и memory; успехи не раздуты ретраями;
- превышение любого порога или отсутствие метрики блокирует локальную приёмку; пороги не выдаются за официальный scoring;
- `block` локальной приёмки не запрещает отправить имеющийся результат до дедлайна: зафиксируй фактические показатели и сохрани честный verdict по `REQUIREMENTS.md`, §2 и §7.1;
- крупные payload до 100 000 токенов проверены отдельно;
- retry/concurrency/recovery пройдены; отдельный overload-профиль проверяет допустимые 429 и восстановление, не заменяя baseline;
- 2000 RPS относится к bonus и не блокирует baseline.

### E. Consumer configuration и extensibility

- есть ограниченный список систем и enabled/disabled;
- для системы настраиваются PII types и разрешение demask;
- инструкция настройки <= 5 предложений;
- новый consumer с существующими правилами добавляется без изменения core-кода;
- новый detector/тип подключается через предусмотренную точку расширения без переписывания всего сервиса.

### F. Security, logging, metrics

- raw PII отсутствует в logs, traces, exceptions, metric labels и committed artifacts;
- логируются основные этапы обработки;
- по запросу логируются detected PII types без исходных значений;
- доступны Latency, RPS и TPS metrics;
- sensitive state минимизирован;
- для принятой модели хранения проверены lifecycle/TTL;
- для внешнего/persistent sensitive storage есть evidence шифрования и безопасного управления ключами;
- secrets не находятся в репозитории;
- нет неподтверждённых заявлений о compliance с внутренними стандартами Банка, ЦБ или законодательством.

### G. Documentation

- README содержит реальные команды установки/запуска/быстрой проверки;
- незапущенные проверки не отмечены как пройденные;
- известные ограничения и открытые вопросы ТЗ не скрыты.

Отсутствующая или не пройденная внешняя проверка — блокер подтверждения submission readiness.

## Короткий выход

```text
Mode: task | submission
Verdict: pass | pass with follow-up | block
Acceptance / fresh verification: check -> result
Review: findings / resolved
Limitations / next step: ...
```

`pass with follow-up` допустим только при выполненных обязательных критериях и неблокирующих замечаниях.
Невыполненный/непроверенный обязательный критерий или P0/P1 означает `block` и статус `blocked`, не Done.
Отправка результата организаторам до срока и verdict о готовности baseline — разные решения; отправка при `block` не превращает непроверенный критерий в выполненный.
Не создавать отдельные commits/reports только ради приёмки.

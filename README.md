# llm-proxy — защита персональных данных при работе с искусственным интеллектом

Проект команды хакатона «Красный Коd». **llm-proxy** находит персональные данные в тексте и временно заменяет их специальными обозначениями, чтобы приложение могло обратиться к языковой модели без передачи ей исходных сведений о человеке. Когда приложение получит ответ модели, сервис восстановит известные ему данные в этом ответе.

**Важно:** llm-proxy сам не обращается к языковой модели. Приложение вызывает наш сервис дважды: до отправки текста модели и после получения её ответа.

## Как это работает

```text
Приложение пользователя
        │  исходный текст
        ▼
llm-proxy: поиск и замена персональных данных
        │  текст со специальными обозначениями
        ▼
Приложение → языковая модель → Приложение
        │  ответ модели с теми же обозначениями
        ▼
llm-proxy: восстановление известных данных
        │  ответ модели с восстановленными данными
        ▼
Приложение пользователя
```

Пример с **вымышленным** адресом электронной почты:

| Этап | Текст |
| --- | --- |
| Исходный запрос | «Напишите на ivan@example.com.» |
| После маскирования | «Напишите на `<EMAIL_1>`.» |
| Ответ языковой модели | «Сообщение можно отправить на `<EMAIL_1>` сегодня.» |
| После восстановления | «Сообщение можно отправить на ivan@example.com сегодня.» |

При первом обращении сервис ищет персональные данные и заменяет их обозначениями, например `<EMAIL_1>`. Временная зашифрованная запись связывает эти обозначения с исходными значениями. При повторном обращении с тем же `payload_id` сервис восстанавливает **только известные обозначения**, оставляя остальной текст ответа модели без изменений. Повтор исходного запроса возвращает тот же результат маскирования. Неизвестные обозначения сервис не угадывает.

Сейчас для демонстрационной настройки используется обратимый формат `<ТИП_номер>` с английскими техническими названиями типов, например `<EMAIL_1>`. Это выбранный командой формат, а не подтверждённый организаторами единый образец.

## Возможности

- **Поиск персональных данных:** ФИО, сведения из паспорта и водительского удостоверения, даты и места рождения, адреса и их части, телефоны, электронная почта, ИНН, реквизиты банковских карт и другие категории из [требований](docs/REQUIREMENTS.md).
- **Учитывание контекста:** сервис старается не заменять обычные даты, упоминания известных людей и адреса организаций, если они не относятся к персональным данным в запросе.
- **Восстановление ответа:** известные обозначения могут повторяться и менять порядок; новый текст модели при этом сохраняется.
- **Настройки для разных приложений:** можно разрешать или запрещать отдельные категории данных и восстановление.
- **Ограниченное хранение:** соответствия хранятся в Redis в зашифрованном виде и автоматически удаляются по истечении срока. Исходные персональные данные не должны попадать в журналы работы и технические показатели.

## Попробовать публичную версию

Приложение развёрнуто на Railway: **[llm-proxy — публичный адрес](https://llm-proxy-production-84c7.up.railway.app)**. Площадка предоставляет защищённое HTTPS-соединение; длительная доступность зависит от ограничений пробного тарифа.

- [Проверка доступности](https://llm-proxy-production-84c7.up.railway.app/healthz) — ожидаемый ответ: `{"status":"ok"}`. Эта проверка подтверждает, что приложение отвечает, но не проверяет доступность временного хранилища.
- [Интерактивное описание запросов](https://llm-proxy-production-84c7.up.railway.app/docs) — позволяет изучить формат обращения.

Пример первого запроса на маскирование (для терминала с `curl`):

```bash
curl -X POST "https://llm-proxy-production-84c7.up.railway.app/process" \
  -H "Content-Type: application/json" \
  --data '{"payload":"Напишите на ivan@example.com.","payload_id":"readme-demo-001"}'
```

В ответе появится поле `result` с текстом, в котором адрес заменён обозначением. Чтобы восстановить данные, отправьте **текст из поля `result`** в `payload`, сохранив тот же `payload_id`. Можно также передать новый текст с полученным обозначением, как в примере выше. Для новой независимой проверки используйте новый `payload_id`.

**Не отправляйте реальные персональные данные в публичную демонстрацию:** её проверяемая совместимость с системой организаторов ещё не подтверждена, а сам интерфейс `/process` не требует отдельной авторизации.

## Запустить на своём компьютере

Нужны [Git](https://git-scm.com/) для получения исходников и [Docker с Docker Compose](https://docs.docker.com/compose/) для запуска. Устанавливать Python на компьютер для этого способа **не требуется**.

1. Получите [исходный код](https://github.com/rp-alpha-vibe/llm-proxy) (репозиторий может быть закрыт, поэтому нужен доступ) и перейдите в папку проекта:

   ```bash
   git clone https://github.com/rp-alpha-vibe/llm-proxy.git
   cd llm-proxy
   ```

2. Скопируйте образец настроек в файл `.env`: в Linux/macOS выполните `cp .env.example .env`, в PowerShell — `Copy-Item .env.example .env`. Укажите в нём `LLM_PROXY_ENCRYPTION_KEY`: случайный ключ из **32 однобайтовых символов** (ASCII). Генерируйте его локально и не публикуйте. Оставьте `LLM_PROXY_DEFAULT_CONSUMER_ID=alfa_tester`, чтобы использовать демонстрационные настройки.

3. Запустите приложение вместе с временным хранилищем:

   ```bash
   docker compose up --build -d
   ```

4. Проверьте доступность и выполните запрос:

   ```bash
   curl http://localhost:8000/healthz
   curl -X POST "http://localhost:8000/process" \
     -H "Content-Type: application/json" \
     --data '{"payload":"Напишите на ivan@example.com.","payload_id":"local-demo-001"}'
   ```

   Для восстановления передайте полученное значение `result` с тем же идентификатором `local-demo-001`. Завершить работу: `docker compose down`.

**Настройка другого приложения:** добавьте его в раздел `systems` файла `config/systems.example.yaml` и укажите `enabled` (доступ), `pii_types` (категории), `allow_demask` (разрешение восстановления) и `mask_strategy` (формат обозначений). Установите `LLM_PROXY_DEFAULT_CONSUMER_ID` в идентификатор этого приложения и перезапустите контейнеры. Текущий публичный интерфейс не принимает идентификатор приложения в запросе: активная настройка выбирается при развёртывании.

## Архитектура в двух словах

```text
            HTTP-запрос POST /process
                       │
                       ▼
        Приложение (Python / FastAPI)
          ├─ выбирает правила обработки
          ├─ находит и заменяет данные
          └─ восстанавливает известные значения
                       │
                       ▼
          Redis: временные зашифрованные
             записи для восстановления
```

Основная логика работает внутри одного приложения. Redis служит только временным хранилищем, недоступным напрямую из интернета. Внешняя языковая модель **не входит** в состав llm-proxy. Подробнее: [архитектура](docs/ARCHITECTURE.md).

## Результаты и ограничения

В **локальном** испытании команда получила 300 001 успешную операцию за пять минут (около 1000 операций в секунду), без ошибок и ответов об ограничении нагрузки. Для 95% операций время ответа не превышало 21,78 мс. Локальная проверка качества на **46 синтетических примерах** дала F1 = 1,0 и точное восстановление исходного текста во всех соответствующих проверках. Это результаты испытаний команды, а **не оценка организаторов**.

Публичная версия на Railway доступна для функциональной демонстрации и прошла короткий probe на 100 операций в секунду без ошибок. Полный профиль 1000 операций в секунду за 300 секунд **не прошёл**: около 33% запросов завершились ошибкой, получено 76 483 ответа 429, а p95 достиг примерно 10 секунд. [Подробный отчёт](submission/railway-load-probe-2026-09-23.md). Доказательство 1000 операций в секунду относится только к локальному прогону; совместимость с официальной проверяющей системой организаторов также ожидает подтверждения.
